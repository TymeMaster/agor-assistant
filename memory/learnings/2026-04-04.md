# Learnings: 2026-04-04

## Claude Code rate_limit_event discovery

### How to detect rate limit status programmatically

`claude -p --output-format stream-json --verbose "ok"` emits a `rate_limit_event` JSON line with account usage state.

**Critical implementation constraints:**
- `--bare` flag suppresses `rate_limit_event` — cannot use it
- Running from a directory with CLAUDE.md causes full agent startup → timeout; must `cd /tmp` first
- `--model haiku` is optimal probe (~$0.004), identical data to Opus ($0.034)

### Rate limit states observed

| State | `status` field | When |
|-------|---------------|------|
| OK | `allowed` | Normal usage (<90%) |
| Warning | `allowed_warning` | Usage >=90% (field `surpassedThreshold: 0.9`) |
| Rejected | `rejected` | Hard limit (seen once, possibly load-dependent) |

### Key findings

1. **Rate limit is account-level**, not per-model. Haiku/Sonnet/Opus all return identical rate_limit_event.
2. **`allowed_warning` is the practical limit signal.** At 100% usage on a low-traffic day (weekend), API still returns `allowed_warning` not `rejected`. The `rejected` state may depend on global infrastructure load.
3. **JSON response shape varies by state.** `allowed` includes `overageStatus`/`overageResetsAt`. `allowed_warning` replaces those with `utilization`/`surpassedThreshold`. Code must handle missing fields.
4. **Orchestration should conserve on `allowed_warning`**, not wait for `rejected` which may never come during low-traffic periods.
